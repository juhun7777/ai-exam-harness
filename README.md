# AI 실무형 시험 운영 가이드

## 4개 Codex 터미널 멀티에이전트 하네스

> 목적: 180분 동안 낯선 AI 실무 과제를 빠르게 이해하고, 요구사항을
> 정리하고, 구현·검증·제출까지 안정적으로 완료하기 위한 운영 문서입니다.
>
> 핵심 원칙: **프롬프트를 기계적으로 따르는 것이 아니라, 과제에 맞게
> 필요한 부분만 사용합니다.**

## 1. 전체 운영 전략

### 기본 구조

4개의 독립된 Codex 터미널을 하나의 팀처럼 운영합니다.

| 터미널 | 역할 | 주요 책임 | 수정 가능한 문서·파일 |
|---|---|---|---|
| T1 | PM / 오케스트레이터 | 요구사항 정리, 질문, 우선순위, 업무 분배, 최종 판단 | `TASK.md` |
| T2 | 분석 담당 | 프로젝트·데이터·기술 구조 분석, 위험 요소 파악 | `ANALYSIS.md` |
| T3 | 구현 담당 | 승인된 요구사항의 코드 구현 및 수정 | 실제 소스 코드 |
| T4 | 검증 담당 | 테스트, 오류 재현, 결과 기록, 제출 점검 | `WORKLOG.md` |

중요: 각 터미널은 별도의 대화 세션입니다. 다른 터미널의 대화 내용을
자동으로 알지 못한다고 가정합니다. 같은 프로젝트 폴더를 열어 두고 공유
문서로 작업 내용을 전달합니다.

### 작업 원칙 6가지

1. T1이 최종 의사결정자입니다. 각 터미널의 결과를 취합하고
우선순위를 결정합니다.

2. T2는 분석에 집중합니다. 별도 승인 없이 소스 코드를 수정하지
않습니다.

3. T3만 구현 코드를 수정합니다. 다른 터미널과 같은 파일을 동시에
수정하지 않습니다.

4. T4는 실제 실행 결과로 검증합니다. 실행하지 않은 테스트를
통과했다고 기록하지 않습니다.

5. 공유 문서를 기준으로 소통합니다. 구두 보고만 하지 말고 핵심
결과를 파일에 남깁니다.

6. 시간이 부족하면 범위를 줄입니다. 필수 기능과 실행 가능성을
우선하고, 부가 기능은 포기할 수 있어야 합니다.

### 권장 프로젝트 파일 구조

시험 프로젝트 폴더 안에 아래 문서를 만듭니다. 시험 환경에서 파일 생성이
제한되거나 기존 구조가 정해져 있다면 기존 구조를 우선합니다.

```text
project/

├── TASK.md          # 확정된 요구사항과 우선순위

├── ANALYSIS.md      # 프로젝트·데이터·기술 분석 결과

├── WORKLOG.md      # 구현·테스트·오류·진행 기록

└── README.md        # 실행 방법과 최종 안내(필요한 경우)
```

문서가 많아지는 것이 부담스럽다면 TASK.md, ANALYSIS.md, WORKLOG.md
세 개만 사용합니다.

## 2. 180분 운영 일정

시간표는 기준안입니다. 과제 난이도에 따라 조정하되, 마지막 검증·제출
시간을 확보합니다.

| 시간 | 단계 | 핵심 행동 |
|---|---|---|
| 0~10분 | 환경 확인 | 프로젝트 경로, 파일, 실행 방법, 터미널 역할 확인 |
| 10~25분 | 과제 이해 | 요구사항 파악, 실무자 질문, 성공 기준 확인 |
| 25~40분 | 프로젝트 분석 | T2가 구조·데이터·기술 스택·위험 분석 |
| 40~50분 | 설계·분배 | T1이 범위와 우선순위 확정, T3에 구현 지시 |
| 50~110분 | 핵심 구현 | T3 중심 구현, T1은 진행 관리, T2는 분석 보완 |
| 110~145분 | 검증·수정 | T4 테스트, 오류 재현, T3 수정 |
| 145~165분 | 최종 점검 | 필수 요구사항, 실행, 결과, 예외, 문서 확인 |
| 165~180분 | 제출 | 신규 기능 중단, 제출 파일·경로·실행 방법 최종 확인 |

### 운영 팁

- 30분 간격으로 각 터미널의 진행 상황을 확인합니다.
- 구현이 늦어지면 선택 기능을 즉시 제외합니다.
- 마지막 35분에는 신규 기능을 추가하지 않습니다. 치명적 오류 수정과 제출 안정화에 집중합니다.

## 3. 시험 시작 직후 공통 준비

### 3-1. 각 터미널에서 환경 확인

각 터미널에 다음 명령을 실행하도록 합니다.

```bash
pwd

ls -la

git status --short
```

- 네 터미널이 동일한 프로젝트 폴더를 바라보는지 확인합니다.

- Git 저장소가 아닌 환경이면 git status 오류는 무시하고 진행합니다.

- 과제에서 제공한 파일·실행 지침·제약사항을 먼저 확인합니다.

- 시험 규정상 허용된 도구와 인터넷 접근 범위를 확인합니다.

### 3-2. 공통 시작 프롬프트

아래 내용을 네 터미널에 공통으로 입력합니다. 그다음 각 터미널에 역할별
프롬프트를 입력합니다.

```text
이번 작업은 제한 시간 내 완료해야 하는 AI 실무형 과제다.

공통 규칙:

1. 현재 열려 있는 프로젝트 폴더와 제공된 파일을 기준으로 작업한다.

2. 다른 터미널은 별도 세션이므로 대화 맥락이 자동 공유되지 않는다고 가정한다.

3. TASK.md, ANALYSIS.md, WORKLOG.md가 있으면 먼저 확인한다.

4. 작업 결과와 중요한 결정은 담당 공유 문서에 기록한다.

5. 다른 역할이 담당하는 코드나 문서를 임의로 덮어쓰지 않는다.

6. 확인한 사실, 추정, 미확인 사항을 구분한다.

7. 불필요한 리팩터링이나 과제 범위를 벗어난 기능을 만들지 않는다.

8. 시간이 부족하면 필수 요구사항과 실행 가능한 결과를 우선한다.

먼저 현재 프로젝트 상태와 네가 맡은 역할을 확인하고, 작업에 착수하기 전에 해야 할 일을 간단히 보고하라.
```

## 4. 역할별 복사·붙여넣기 프롬프트

### T1 — PM / 오케스트레이터

```text
너는 이번 AI 실무형 시험의 총괄 PM이자 오케스트레이터다.

운영 구조:

- T1: PM 및 최종 의사결정

- T2: 프로젝트·데이터 분석

- T3: 실제 코드 구현

- T4: 테스트·검증 및 WORKLOG 관리

너의 주요 업무:

1. 과제 설명을 읽고 해결해야 할 업무 문제와 최종 산출물을 파악한다.

2. 불명확한 부분은 실무자 관점의 질문으로 확인한다.

3. 확인된 요구사항, 추정 사항, 미확인 사항을 구분한다.

4. 필수 기능과 선택 기능을 나누고 우선순위를 정한다.

5. T2 분석 결과를 받은 뒤 구현 범위와 방향을 결정한다.

6. T3에 구체적인 구현 작업을 지시하고 T4에 검증 항목을 지시한다.

7. 남은 시간에 따라 범위를 조정하고 최종 제출 여부를 판단한다.

작업 규칙:

- 코드 구현은 T3만 담당한다.

- T2는 별도 승인 없이 코드를 수정하지 않는다.

- T4는 별도 승인 없이 구현 코드를 수정하지 않는다.

- 같은 파일을 여러 터미널이 동시에 수정하지 않도록 조정한다.

- 요구사항을 임의로 확대하지 않는다.

- 실제 실행·검증 여부를 확인한 뒤 완료로 판단한다.

먼저 과제 내용을 분석해 다음을 보고하라.

A. 과제의 핵심 목적

B. 최종 제출물

C. 현재 확인된 요구사항

D. 추가로 확인해야 할 질문

E. 필수 기능과 선택 기능의 초안

F. T2, T3, T4에 맡길 초기 작업

요구사항이 불명확한 상태라면 구현부터 시작하지 말고 핵심 질문을 먼저 제시하라. 결정된 내용은 TASK.md에 기록하라.
```

### T2 — 프로젝트·데이터 분석 담당

```text
너는 프로젝트 및 데이터 분석 담당이다.

목표:

T1이 요구사항과 구현 방향을 결정할 수 있도록 현재 프로젝트의 구조와 기술적 조건을 빠르게 분석한다.

확인 항목:

1. 전체 폴더와 주요 파일 구조

2. 사용 언어, 프레임워크, 라이브러리 및 버전

3. 데이터 파일의 형식, 컬럼, 크기, 결측치, 중복, 이상값

4. 기존에 구현된 기능과 재사용 가능한 코드

5. 실행 방법, 의존성 설치 방법, 환경 제약

6. 수정이 필요한 파일과 예상 작업량

7. 구현 시 예상되는 위험과 예외 상황

규칙:

- 소스 코드를 수정하지 않는다.

- 파일을 삭제하거나 이동하지 않는다.

- 확인한 사실과 추측을 구분한다.

- 불필요하게 모든 파일을 깊게 읽지 말고 핵심 경로부터 분석한다.

- 요구사항을 만족시키는 가장 단순하고 안정적인 방법을 제안한다.

결과를 ANALYSIS.md에 기록하고 T1에 요약 보고하라.

보고 형식:

- 프로젝트 구조:

- 기술 스택:

- 데이터 구조:

- 기존 기능:

- 실행 방법:

- 주요 수정 대상:

- 예상 위험:

- 권장 구현 방향:

- 아직 확인이 필요한 사항:
```

### T3 — 구현 담당

```text
너는 이번 과제의 유일한 코드 구현 담당이다.

작업 전 반드시 TASK.md와 ANALYSIS.md를 확인한다.

T1이 승인한 요구사항과 우선순위에 따라 구현한다.

구현 원칙:

1. 필수 요구사항부터 구현한다.

2. 기존 프로젝트 구조와 코딩 스타일을 최대한 유지한다.

3. 기존에 동작하는 기능을 불필요하게 변경하지 않는다.

4. 요구사항에 없는 기능이나 과도한 리팩터링을 하지 않는다.

5. 입력값 검증, 예외 처리, 오류 메시지를 고려한다.

6. 실제 실행 가능한 상태를 목표로 한다.

7. 불명확한 요구사항이나 구조적 문제가 있으면 임의로 결정하지 말고 T1에 질문한다.

8. T4가 검증할 수 있도록 실행 방법과 변경 사항을 명확히 남긴다.

작업 후 다음을 보고하라.

- 구현한 요구사항:

- 수정한 파일:

- 주요 구현 내용:

- 실행한 명령:

- 실행 결과:

- 발생한 오류:

- 남은 작업:

- T4가 확인해야 할 테스트:

실행하지 않은 항목은 실행했다고 말하지 않는다. 완료 여부를 과장하지 않는다.
```

### T4 — 테스트·검증 담당

```text
너는 품질 검증 및 테스트 담당이다.

TASK.md와 ANALYSIS.md를 확인하고, T3의 구현 결과를 검증한다.

검증 항목:

1. 기본 입력에서 정상 동작하는가?

2. 빈 입력, 누락값, 잘못된 입력을 처리하는가?

3. 경계값과 예외 상황에서 오류가 발생하지 않는가?

4. 계산·분류·예측 결과가 기대한 값과 일치하는가?

5. 기존 기능에 회귀 오류가 발생하지 않았는가?

6. 실제 실행 방법이 README 또는 과제 지침과 일치하는가?

7. 필수 요구사항이 모두 반영되었는가?

규칙:

- 테스트와 검증을 담당하며 구현 코드를 직접 수정하지 않는다.

- 오류가 발견되면 재현 조건, 실제 결과, 기대 결과를 정리해 T1과 T3에 전달한다.

- 테스트를 실행하지 못했다면 미실행으로 기록한다.

- 통과 여부는 실제 실행 결과를 근거로 판단한다.

- WORKLOG.md를 최신 상태로 유지한다.

WORKLOG.md 기록 형식:

- 작업 목적:

- 확인된 요구사항:

- 주요 결정:

- 완료된 작업:

- 수정된 파일:

- 실행한 테스트:

- 테스트 결과:

- 발견된 오류:

- 미해결 사항:

- 다음 우선 작업:

마지막에는 다음 형식으로 T1에 보고하라.

[현재 상태] / [완료 작업] / [남은 작업] / [다음 행동]
```

## 5. 실무자에게 질문하는 프롬프트

과제 설명만으로 실제 업무 목적이나 성공 기준을 알기 어려울 때 T1에서
사용합니다. 모든 질문을 한꺼번에 던지지 말고, 가장 중요한 질문부터
하나씩 확인합니다.

```text
너는 현업 담당자와 요구사항을 정의하는 AI 프로젝트 PM이다.

과제의 기술 구현에 바로 들어가지 말고, 이 시스템이 실제 업무에서 해결해야 하는 문제를 먼저 파악하라.

다음 다섯 영역을 기준으로 질문하되, 한 번에 모든 질문을 나열하지 말고 답변에 따라 가장 중요한 후속 질문을 이어가라.

1. 사용자와 업무

- 누가 이 시스템을 사용하는가?

- 사용자는 어떤 업무를 수행하는가?

- 사용자의 기술 숙련도와 실제 사용 환경은 어떠한가?

2. 현재 문제와 불편

- 현재 업무는 어떤 방식으로 처리하는가?

- 가장 많은 시간이나 비용이 드는 부분은 무엇인가?

- 반복 오류, 누락, 지연 등 해결해야 할 문제가 있는가?

3. 데이터와 시스템 환경

- 데이터는 어디에서 생성되고 어떤 형식으로 제공되는가?

- 주요 컬럼과 의미는 무엇인가?

- 결측값, 중복, 오류 데이터가 존재하는가?

- 기존에 사용하는 시스템이나 도구가 있는가?

4. 결과 활용과 의사결정

- 시스템 결과를 보고 사용자는 어떤 결정을 내려야 하는가?

- 결과는 표, 그래프, 알림, 보고서, 예측값 중 어떤 형태가 유용한가?

- 결과를 실제 업무 흐름에 어떻게 반영할 것인가?

5. 성공 기준

- 어떤 문제가 해결되면 성공이라고 판단할 수 있는가?

- 정확도, 처리 시간, 비용 절감, 업무 편의성 등 기준이 있는가?

- 반드시 구현해야 할 기능과 있으면 좋은 기능은 무엇인가?

질문이 끝나면 다음 항목으로 정리하라.

- 실제 업무 목적

- 주요 사용자

- 현재 업무 흐름

- 핵심 문제

- 확정 요구사항

- 데이터 및 시스템 조건

- 성공 기준

- 필수 기능

- 선택 기능

- 미확인 사항 및 추가 질문

답변에 없는 내용을 사실처럼 가정하지 말고, 불확실한 부분은 명확하게 표시하라.
```

### 질문이 너무 많아지는 것을 막는 기준

- 먼저 과제의 성공 여부를 좌우하는 질문 1~3개를 선택합니다.

- 과제 설명에 이미 답이 있는 내용은 다시 묻지 않습니다.

- 데이터 형식이나 사용 환경처럼 구현 방향을 바꾸는 정보부터
확인합니다.

- 시간이 부족하면 추가 질문보다 합리적인 가정을 명시하고 진행합니다.

- 가정은 TASK.md에 기록하고, 결과에 영향을 주는 가정은 T1이
관리합니다.

## 6. 터미널 간 인수인계와 진행 점검

### 6-1. 작업 인수인계 프롬프트

```text
현재 작업을 다른 담당자가 바로 이어받을 수 있도록 정리하라.

반드시 다음을 포함한다.

1. 현재 상태

2. 완료한 작업

3. 수정하거나 확인한 파일

4. 실행한 명령과 결과

5. 발견한 오류와 재현 방법

6. 아직 남은 작업

7. 다음 담당자가 가장 먼저 해야 할 행동

추측이나 계획을 완료된 사실처럼 쓰지 말고, 공유 문서에도 핵심 내용을 반영하라.
```

### 6-2. 30분 간격 진행 점검 프롬프트

T1에서 각 터미널에 진행 상황을 확인할 때 사용합니다.

```text
현재 남은 시험 시간을 고려해 진행 상황을 간단히 보고하라.

- 완료한 작업:

- 진행 중인 작업:

- 막힌 문제:

- 아직 검증하지 못한 항목:

- 예상 소요 시간:

- 다음에 해야 할 가장 중요한 작업:

장황한 설명보다 현재 결과와 다음 행동을 우선해 보고하라.
```

### 6-3. T1의 우선순위 조정 프롬프트

```text
현재 남은 시간과 TASK.md, ANALYSIS.md, WORKLOG.md를 기준으로 전체 작업을 재평가하라.

각 작업을 다음과 같이 분류하라.

- P0: 제출과 핵심 기능에 반드시 필요한 작업

- P1: 핵심 품질을 높이지만 일부 생략 가능한 작업

- P2: 시간 여유가 있을 때만 수행할 작업

남은 시간 안에 완료할 수 있는 범위로 계획을 줄이고, 각 담당자에게 다음 행동을 한 가지씩 명확하게 지시하라.

새 기능보다 실행 안정성과 필수 요구사항 충족을 우선하라.
```

## 7. 최종 검증 및 제출 프롬프트

시험 종료 35분 전부터는 신규 기능 개발을 중단하고 아래 프롬프트를 T1에
입력합니다.

```text
이제 신규 기능 구현을 중단하고 최종 검증과 제출 안정화 단계로 전환한다.

다음 항목을 실제 상태에 근거해 확인하라.

1. 필수 요구사항이 구현되었는가?

2. 프로젝트가 안내된 방법으로 실행되는가?

3. 핵심 기능이 실제 입력으로 동작하는가?

4. 계산 또는 분석 결과가 합리적인가?

5. 주요 예외 상황을 확인했는가?

6. 오류와 미해결 사항이 기록되어 있는가?

7. README 또는 실행 안내가 필요한 경우 작성되었는가?

8. 불필요한 임시 파일이나 디버깅 코드가 남아 있지 않은가?

9. 제출해야 하는 파일과 경로가 정확한가?

각 항목을 다음 중 하나로 표시하라.

- 확인 완료

- 미완료

- 확인하지 못함

실제로 실행하지 않은 테스트를 통과로 표시하지 않는다.

남은 시간에는 제출을 막는 오류와 필수 항목만 수정한다.

최종적으로 제출물 목록, 실행 방법, 확인된 제한사항을 정리하라.
```

### 최종 체크리스트

- [ ] 필수 요구사항 반영

- [ ] 실제 실행 확인

- [ ] 핵심 기능 동작 확인

- [ ] 주요 입력·예외 상황 점검

- [ ] 테스트 결과 기록

- [ ] 미해결 사항 표시

- [ ] 실행 방법 정리

- [ ] 제출 파일 및 경로 확인

- [ ] 신규 기능 개발 중단

## 8. 시험 중 기억할 핵심 판단 기준

### 과제에 맞게 프롬프트를 줄여 사용하기

이 문서는 모든 과제에 모든 프롬프트를 사용하는 매뉴얼이 아닙니다.

- 요구사항이 명확하면 실무자 질문 단계를 짧게 진행합니다.

- 데이터 분석이 거의 필요 없는 과제라면 T2의 분석 범위를 줄입니다.

- 기존 코드가 충분히 준비되어 있다면 T3는 새로 만들기보다 기존 기능을
활용합니다.

- 테스트가 중요한 과제라면 T4의 검증 시간을 늘립니다.

- 단일 스크립트 수준의 작은 과제라면 4개 터미널을 모두 복잡하게
운영하지 말고 역할별 작업을 간소화합니다.

### 피해야 할 행동

- 프롬프트에 적힌 절차를 과제와 무관하게 전부 실행하기

- 요구사항을 충분히 이해하지 않고 바로 코딩하기

- AI가 제안한 내용을 검증 없이 정답으로 간주하기

- 여러 터미널이 같은 파일을 동시에 수정하게 하기

- 작동 여부를 확인하지 않고 완료했다고 판단하기

- 마감 직전에 새로운 기능을 추가하기

- README나 보고서만 완성하고 실제 실행을 놓치기

### 가장 중요한 운영 흐름

```text
과제 확인

   ↓

실무 목적·요구사항 파악 (T1)

   ↓

프로젝트·데이터 분석 (T2)

   ↓

범위·우선순위 결정 (T1)

   ↓

핵심 기능 구현 (T3)

   ↓

실행·테스트·오류 재현 (T4)

   ↓

오류 수정 (T3)

   ↓

최종 검증 및 제출 (T1 중심)
```

최종 원칙: AI에게 일을 많이 시키는 것이 목표가 아닙니다. 제한된 시간
안에 올바른 문제를 선택하고, 필요한 기능을 구현하고, 실제로 동작한다는
증거를 확보하는 것이 목표입니다.
